# 稿件崩溃恢复

当前本地源码提供独立的恢复保护，默认开启；写回原文件的自动保存默认关闭，只有明确开启才生效。旧设置缺少 `recovery` 时按开启处理，缺少 `autosave` 时按关闭处理，已有明确选择均保留。正式发行包未被本任务替换。

在设置（`Ctrl+Shift+P`）调整“崩溃恢复”。开关立即作用于当前会话并尝试记住。设置写入失败时，保留用户本次的保护选择并说明尚未记住；不会逐帧反复写设置。关闭恢复保护不会删除待处理副本，也不会阻止其恢复、稍后处理或明确删除。

恢复副本与原文件自动保存完全独立。更新副本不写原路径，不清除未保存标记，不改变焦点、选区或输入法状态。未命名稿件、主副文档、有路径但尚未保存的正文、当前编码和 BOM 都被保护；换行逐字保留。未编辑的空白新稿不生成记录，已经输入后全部删除的未命名稿仍作为有效空正文保护。

## 发现与恢复

异常退出后再次启动，列表显示名称、来源路径、快照时间（明确标注 UTC）、窗格、正文大小、编码/BOM、内容摘要和独立草稿数量。没有待处理记录就不显示空提示。可以：

- **恢复：** 打开新的未保存副本；恢复正文不绑定原文件，必须由用户主动选择保存位置。即使原文件已删除、移动、变为只读或被外部修改，仍可取回副本。
- **稍后处理：** 保留记录，可通过稿件状态旁的“恢复稿件…”再次打开列表。
- **删除恢复副本：** 明确确认后永久作废该份副本及其草稿。取消删除不改变记录。

当前有未保存稿件时，先按既有流程保存或放弃，再恢复另一份稿件。领取是排他的，恢复期间保留原有效检查点；恢复后再次异常退出仍可恢复。另一活跃实例的稿件不作为崩溃稿件提示，两个实例也不能同时领取同一份记录。

## 独立草稿

公式、图表及尚未同步的表格输入独立保存，不强行合并到正文。恢复后打开“独立草稿”查看和复制；保留节点类型、原范围、原片段和预期内容版本，避免错贴到已变化的节点。无效、冲突或无法安全重新关联的输入都按独立文本处理。

输入法保护以已经交给应用的文字为边界。检查点不会强制结束组合输入，也不会因输入法处于组合状态而长期停止保护此前已提交的正文和草稿。

正文主动保存成功后，较新的正文修改和独立草稿仍保留恢复保障。已恢复的草稿不会因为正文保存而自动删除；确认复制完成后，可用“放弃独立草稿…”单独作废。草稿窗口的关闭按钮只关闭查看界面。

## 时机、可靠性与失败

目标是在停止有效编辑约 2 秒后调度；持续编辑时，以 10 秒周期调度最新快照。计时由重绘计时器推进，不依赖键鼠事件。每窗格至多一个写入任务，没有排队的完整快照，仅保留最新版本信息；旧任务未完成时不能累积线程。超慢存储可能延迟实际提交，恢复承诺始终以最后成功提交的检查点为准。

正文捕获后由后台序列化、校验和写盘。提交采用同目录临时文件、文件同步和原子替换，保留两个有效世代；最新数据损坏时退回此前完整版本。已确认放弃使用持久失效标记，迟到任务不能复活。原文件保存、另存为、重命名及关闭仍使用既有编码、路径和外部修改保护规则。

每份稿件显示恢复状态，与“原文件已保存”区分。失败会保留已有有效版本，显示原因和“重试恢复保护”；解决容量或权限问题后重试。普通写入失败暂停到用户重试；短时锁竞争最多每秒重试，不逐帧忙等，其他稿件有独立任务与错误状态。失效写入失败不会假称放弃成功。

## 本地位置与上限

Windows：`%LOCALAPPDATA%\MDcard\recovery`。Linux：`$XDG_STATE_HOME/MDcard/recovery`，或 `~/.local/state/MDcard/recovery`。验证可用 `MDCARD_RECOVERY_DIR` 指向独立目录，不影响用户正式数据。

| 项目 | 实际上限 |
| --- | --- |
| 每份正文 | UTF-8 16 MiB |
| 每份独立草稿文本总量 | UTF-8 16 MiB |
| 每份独立草稿数量 | 128 |
| 单个序列化世代 | 128 MiB，包含路径、名称、原片段、格式和 JSON 开销 |
| 未处理稿件 | 128 份 |
| 总存储 | 512 MiB，按已存文件与本次临时提交所需空间检查，包含保留世代 |
| 检查点后台写入 | 主副各 1 个，无完整快照队列 |
| 其他恢复后台任务 | 发现 1 个、领取或删除操作 1 个 |

不会按到期或容量静默淘汰未处理稿件。超限、磁盘满或权限错误不破坏上一份有效副本。失活会话的锁文件、无正文的废弃预约和中断临时文件会安全清理；未知格式或全损坏副本保留并允许明确删除。

恢复数据仅在本地应用状态目录。恢复正文不写入诊断报告或上传服务：恢复来源缓冲区的搜索报告正文置空，可能含正文片段的 rich、性能、阅读诊断暂停；UI 验证只导出长度、缓存指纹及状态。恢复文件本身、用户主动复制/保存和人工验收截图是明确的数据取回路径。

## 验证入口与范围

[本次逐项验收](CRASH_RECOVERY_ACCEPTANCE_2026-10-26.md)记录源码/候选身份、命令、原生强制结束重启、自动化与性能原始数据。可复跑：

```text
python scripts/check.py --desktop --acceptance
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked recovery:: -- --nocapture
pwsh -STA -File scripts/verify-recovery-windows.ps1 -Exe <普通候选> -Suite Core
pwsh -STA -File scripts/verify-recovery-windows.ps1 -Exe <普通候选> -FaultExe <独立故障候选> -Suite Drafts
pwsh -STA -File scripts/verify-recovery-windows.ps1 -Exe <普通候选> -Suite Performance
pwsh -File scripts/verify-recovery-storage-windows.ps1 -Container <Linux开发容器>
pwsh -File scripts/verify-recovery-json-reader.ps1
```

本次固定候选在 `artifacts/recovery-2026-10-26/final-r4/`，原生脚本默认指向该目录。新构建使用 `sh scripts/build-recovery-candidates.sh <全新目录>`，脚本失败即停且拒绝覆盖已有候选；重跑新候选时显式传入 `-Exe`、`-FaultExe`。此本地目录不是完整发行包，原生验收使用当前工作区已经准备好的 `renderer/`，由脚本设置 `MDCARD_RENDERER_DIR`；正式包未被替换。源码和候选身份可用 `python scripts/recovery-source-identity.py` 独立复核。

故障候选使用独立的 `acceptance-faults` 编译特性，只有显式设置 `MDCARD_ACCEPTANCE_TABLE_PATCH_FAILURE` 才注入表格同步失败。普通构建没有该故障入口。表格正常输入在同一帧同步正文，没有稳定的未提交窗口；负路径验证会明确区分注入失败与自然发生的冲突。

本任务不声称系统崩溃或物理掉电已被真实测试；文件同步与双世代算法的证据、进程强制终止证据与这些尚未验证的故障范围分别记录。
